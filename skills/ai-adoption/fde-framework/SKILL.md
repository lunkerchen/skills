# FDE 框架（前置部署工程師）

基於范冰《前置部署工程師：人工智慧時代的客戶價值交付秘籍》，2025-2026。

## 一句定義（Bob McGrew）

> **前置部署工程師，是駐紮在客戶現場、填補產品能做的事與客戶需要做的事之間鴻溝的工程師。**

## 不是什麼

| 混淆項 | 關鍵區別 |
|--------|---------|
| 售前 | 售前在簽約前結束、目標贏單；FDE 在簽約後才進入深水區、目標贏結果 |
| 駐場外包 | 駐場按工時結算；FDE 按階段交付、按結果驗收、做完會走 |
| 諮詢顧問 | 顧問對建議負責；FDE 對系統運轉負責，終點是客戶團隊能獨立使用 |
| 產品工程師 | 產品工程師面對抽象用戶；FDE 面對具體客戶（某銀行的風控部） |

## 核心方法論

### PSF（Problem-Solution Fit）— 確保解決對的問題

三關全過才值得做：
1. **痛點檢驗** — 兩個具體：具體的人 × 具體的痛（「客服主管週一早上花 3hr 從 4 個系統手動彙整」≠「提升客服效率」）
2. **經濟性檢驗** — 值多少錢？算人時/錯誤成本/釋放產能
3. **可行性檢驗** — 數據在哪、什麼狀態、準確率門檻多少？

### MVD（Minimum Viable Deployment）

三條軍規：
- **真實數據**，沒有例外。假數據做的驗證 = 概念驗證墳墓第一塊磚
- **縮小切口，不縮小野心** — 做垂直打穿的單點（只做退貨單但做到端到端無人干預）
- **死線以週計** — Palantir 訓練營 1-5 天，Sierra 最快 4 週上線

### 影子工作法

跟著真實用戶過完他真實一天。重點觀察**變通**而非流程：
- 員工為什麼堅持導出到表格裡再算一遍？
- 哪份數據是大家真正信任的？（往往非官方系統那套）
- 哪裡有「這事得問老王」的隱性知識？

### 進場盡調五份地圖

數據地圖 / 流程地圖（含變通，標註時間消耗最大 + 出錯代價最大 + 情緒最激烈的三點）/ 組織地圖 / 系統地圖 / 政治地圖（動了誰的乳酪？被替代者出路？）

### 三級複製槓桿（規模化命脈）

| 級別 | 內容 | 效果 |
|------|------|------|
| 一級：知識複製 | 打法手冊、檢查清單、培訓材料 | 新人上手 1 年→3 月 |
| 二級：組件複製 | 連接器、評估框架、部署模板 | 下個團隊起點不是零 |
| 三級：產品複製 | 反覆出現的定制抽象為平台能力 | 消滅交付成本 |

McGreww 檢驗：每後續客戶的定制量必須遞減。不遞減 = 人天生意。

### 健康度四信號

使用信號（週活趨勢）/ 價值信號（業務指標 vs 當初靶子）/ 關係信號（支持者在職、高層接觸）/ 商業信號（用量/帳單比、合同到期）。合成健康分，跌破警戒線觸發干預。

QBR 三紀律：講客戶語言 / 讓客戶業務方當主角 / 以下季價值計劃收尾。

### 成果計價四檔

用量（$/token）→ 行為（$/完成退貨）→ 結果（$/成功解決會話，Sierra）→ 價值分成（按省下成本提成）。越貼近價值天花板越高，測量成本也越高。

### 產品化四問

1. 個性還是共性？（3+ 客戶相同痛點才算產品信號）
2. 泛化代價 < 收益？
3. 非工程師能用？
4. 收編後現場還有空間？（平台讓常見的事容易，現場讓不可能的事發生）

## Palantir 訓練營（MVD 工業化標杆）

第 0 天鎖定核心戰場 → 第 1 天打通數據建 Ontology → 第 2-3 天背靠背寫程式碼 → 第 4-5 天高管親手操作拍板。銷售週期 9-12 月→數週，轉化率約 75%。

## FDE 常用指標

**交付層**：TTV（以週計） / POC 轉化率 / 評估達標率
**客戶層**：激活率 / 使用深度 / 健康度 / 支持者覆蓋
**商業層**：NRR（及格 100%，優秀 120%）/ 交付毛利率 / 定制遞減率
**組織層**：現場→產品回流速率 / 複用率 / 人均產能 / 團隊續航

## 紅旗信號

- 只有 IT 部門，沒有業務負責人
- 「只許看不許碰」— 拒絕提供真實數據
- 「宇宙級需求」— 第一次就要覆蓋全公司
- 需求蝗蟲：預算充足但吸乾團隊不產複利

## 職業道德六底線

1. 數據主權屬於客戶
2. 誠實報告結果（包括壞消息）
3. 不製造依賴
4. 把被替代的人當回事
5. 對不合規要求說不
6. 記住你代表「技術」本身

## 陷阱

- FDE 最大敵人是自己成本結構：精英被泥潭拖住 = 機會成本雪崩
- 出差 25-50%，倦怠是真實風險
- 定制債務：放任客製功能長滿部署 → 利潤被吃掉
- 沒有平台底座的 FDE = 純人力外包
- 中國市場：客戶習慣買斷+專案驗收，混合制是活路

## 職業面：產業現況與入門路線（Adrian Punk, 2026-07）

來源：X Article「最近大火的 AI 岗位，FDE 到底是干嘛的？普通人怎么上车？」@AdrianPunk115（2026-07-31）。與上半部方法論互補 — 這半部是市場信號 + 個人轉職地圖。

### 市場信號（為何此刻爆火）

- LinkedIn：FDE 相關職缺 2023→2025 成長 **42 倍**
- OpenAI：2026-05 成立 Deployment Company，初始投入 **40 億美元+**，收購帶進約 150 名部署工程師
- AWS：投入 **10 億美元**，準備把數千名工程師送進客戶團隊
- 底層邏輯：AI 已從「比模型」走到「比落地」。模型榜 0.1 分客戶無感；能接進舊系統、跑進工作流、省下真金白銀的 AI 客戶才願意持續付錢

### FDE 一天實況（連鎖零售「智能補貨 Agent」案例）

第一週可能一行代碼都沒寫：找門店負責人看現況補貨、找供應鏈確認規則、找 IT 看接口、找安全部門談權限。之後才進工程階段：接庫存/銷售/訂單系統 → 清歷史數據 → 寫模型調用與 Agent 工作流 → 做員工願意打開的頁面 → 加登入/權限/日誌/監控 → 準備測試數據 → 人工複核與失敗兜底。上線後盯使用率、建議採納率、缺貨率，以及「員工為什麼又偷偷回到 Excel」。

六步壓縮：**找問題 → 拆流程 → 做方案 → 寫系統 → 推上線 → 看結果**。需求只是起點，結果才是交付。

### 與鄰近崗位的邊界

FDE 的 E 依然是 Engineer：OpenAI FDE 招聘要求能寫/審查生產級前後端代碼；Palantir 應屆也要求熟至少一門程式語言。完全繞開代碼的路走不通 — 但偏好業務+客戶、不想長期寫生產代碼的人，可看 Deployment Strategist / AI 產品經理 / 行業解決方案顧問 / 客戶成功 / AI 諮詢。

### 普通人五條轉職路（先盤自己已有的，再補缺的那半）

| 原有背景 | 已具備 | 要補的 |
|---|---|---|
| 軟體工程師 | 生產代碼、系統思維 | 用戶訪談、業務流程、需求範圍、ROI、採用率 |
| 數據分析師 | SQL、指標、業務溝通 | 工程化：Notebook→服務、接 API、登入/權限、部署/監控、故障恢復 |
| 產品/諮詢/行業運營 | 行業經驗（製造排產、金融合規、零售庫存） | 程式、資料庫、API、部署，做出能運行的系統 |
| 售前/實施/解決方案架構師 | 客戶、企業內採購/權限/舊系統知識 | 跨過代碼坎：Demo→開發、測試、部署、維護 |
| 完全零基礎 | — | 先練一項硬能力（數據分析/AI 營運/技術支援/實施顧問/初級開發），FDE 很少是職業第一站 |

### 半年路線（避免「收藏夾很滿，簡歷還是空的」）

1. **第 1-2 月補工程底座**：Python/TypeScript、SQL、HTTP/JSON/API、Git、錯誤處理與測試、Docker 基礎部署。驗收標準只有一條：獨立做出帶資料庫+API 的小應用，部署後別人能打開用。
2. **第 3-4 月做完整 AI 應用**：加上模型 API、RAG、Tool Calling、結構化輸出、日誌、Evals、失敗重試、人工複核。別做「上傳 PDF 然後聊天」，選具體任務（整理銷售線索/客服查知識起草回覆/檢查報銷/運營異常提醒/設備故障查詢）。
3. **第 5-6 月找真實用戶**：3-5 人連續用兩週，記錄原/新流程耗時、使用次數、建議採納率、人工處理錯誤、放棄原因。真實用戶會翻出隱藏問題：數據髒、權限不夠、頁面難用、流程天天變、成本太高。整理成案例：業務背景 → 原流程 → 為何選這題 → 架構 → 數據與權限 → 評估方法 → 使用結果 → 失敗與調整 → 可複用部分。

### 求職關鍵字（崗位名稱未統一）

Forward Deployed Engineer / Forward Deployed AI Engineer / Applied AI Engineer / AI Deployment Engineer / Solutions Engineer / AI Solutions Architect / Deployment Strategist / AI 應用交付工程師 / AI 解決方案工程師 / Agent 工程師。

### 面試準備

模糊題（例：「醫院想用 AI 縮短患者等待時間，你會怎麼做？」）先別選模型 — 問清楚：患者在哪些環節等、誰在做排隊分流、現在平均等多久、數據在哪、哪些決定必須醫護完成、成功看什麼指標。面試官想看你能不能把模糊問題一點點變清楚。

### 避坑：真 FDE vs 換皮駐場

FDE 爆紅後同名不同崗。面試直接問：寫的代碼進哪個倉庫？團隊歸產品/工程還是專案交付？考核看採用率和業務指標還是只按期驗收？現場問題怎麼進產品路線圖？專案結束誰負責長期運行？過去三個專案沉澱了哪些可複用組件？出差/駐場/on-call 各佔多少？

- **真 FDE**：寫生產代碼、對結果負責、經驗能回到產品
- **換皮駐場**：按人天計費、圍著驗收轉、每個專案重新做（= 上文的定制債務 + 純人力外包紅旗）

若公司讓你背結果卻不給數據權限、技術決策權、產品支持 → 這份工作會很累。職位名稱很新，工作方式可能一點沒變。

## 徐智昊《FDE 藍皮書》(fhxqtech.com, 2026)增補

來源：方好心晴 FDE 藍皮書 PDF + 章節頁。作者為漢得 IT 諮詢現場交付出身 → SaaS 產品 → 一人公司。與范冰書互補：這本是「企業內部怎麼落地 FDE」的組織改造視角（含中國語境）。

### 核心模型：Delta + Echo 與雙循環

- **Delta + Echo 雙子星**：業務側(Echo,理解需求)+技術側(Delta,做出系統)同 pod、對同一業務結果負責。建設性對抗是設計出來的——Delta 質疑需求可行性, Echo 質疑方案是否解決真問題。雛形=漢得業務顧問+技術顧問,但那時分屬不同專業線、考核不同、利益衝突。理想=合一個人(信息不割裂:顧問聊天時工程師在寫碼=信息斷層)。雙人只是過渡,方向是合一。
- **四核心原則**：前線優先(錨點,唯一紅線)>工程師前移(手段)>產品-前線閉環(防浪費)>迭代共創(工作方式)。
- **雙循環飛輪**：內循環=單項目交付(發現問題→畫工作流→設計方案→構建→部署→追蹤效果);外循環=閃光點即時回流→產研標準化→供所有後續項目用。並行非串行;外循環斷了=駐場外包。
- **70% 沉澱率是觀察不是 KPI**：沉澱太低=更貴駐場;100%=沒空間處理特殊。把它拆成個人 KPI 會把 FDE 和產品推到對立面。
- **閃光點**：多是極小具體的發現(數據格式相同、審批流程重複、臨時腳本邏輯通用)。即時捕捉,五分鐘討論,不等到週會。判斷標準:這件事會不會讓下一個客戶的部署更快?
- **沉澱三類**：通用模式(優先最高)/行業模板(需抽象)/純定制(留定制層)。分層架構:客戶定制層→平台適配層→核心平台層。

### 組織定位與考核

- **匯報線決定行為**:FDE 必須掛產研。三模型:工程主導(Palantir/Anthropic)、產品主導(OpenAI/Cohere)、GTM 主導(CRO)→18 個月內變諮詢公司、產品腐爛。閉環要靠結構(同團隊每天同步)不靠流程(每週匯總 50% 門檻,依賴多個條件同時成立,現實常不成立)。
- **消滅邊界不是劃界**:SE/SA/實施/CS 各管一段=交接=效率流失根源。方向是所有人往 FDE 走。過渡:從最高價值場景開始、FDE 當標杆示範、平台完善後個人能力要求降低。
- **考核兩維度**:前端交付為主(TTV/響應速度/生產採用率/客戶滿意度);反哺為輔,不量化成 KPI(產品化率當考核→FDE 想的是產品接不接受,不是怎麼解決問題=前線優先變產品優先)。
- **退化紅燈**:開始用計費工時考核 / 向 CRO 匯報 / 客戶倉庫的一次性定制代碼 90 天沒人審視抽象。

### 落地路徑(企業內部)

- **第一個試點選財務或 HR 招聘**——內部信息流節點:試錯可控、摩擦大、ROI 可量化。不要選:客服(太個性化)/產研(沒有業務-技術斷層)/採購(被 ERP+合規卡死)。
- **從兩側拉人配對作戰**:業務側 1-2 人(用現有工具做 Demo)+ 技術側 1-2 人(把 Demo 變系統)。做 FDE 的過程中變成 FDE。跑通後裂變:第二批跟第一批配對(有帶教),第三批內部自然識別。
- **硬性規則**:首次集成 ≤14 天 / 生產上線 ≤90 天(做不到就終止)/ 業務側必須有對接人否則不啟動 / 每項目至少一個核心產品改進 / 技術側 120 天撤出(業務側不撤,已變成能自己迭代工具的人)。
- **業務發起人門檻**:沒有願意騰時間配合、衝突時拍板用新的、困難時不退縮的業務發起人 → 不要開始,等。
- **執行三步**:跟著走一遍(坐業務工位旁親手走流程)→ 第一天交付能跑原型(最痛一點,粗糙但真實)→ 逐步擴展(增量交付,每解決一個問題立刻給用)。
- **AI 編程是前提**:業務人員能自己做工具是 Agentic Coding 時代才成立。演進路:單項目開發→標準化配置→低代碼→Agentic Coding。沒有這前提,「業務側學會自己迭代」是空談。

### 作戰節奏與指標

- 四層節奏:每日 standup(前線協同)/ 每週 pod 評審(風險、依賴、採用)/ 每月架構安全評審(模式抽象、控制繼承)/ 每季 portfolio review(Kill / Scale / Productize)。即時沉澱在前線節奏,治理在周/月/季節奏,並行不衝突。
- 四指標:TTV(上線兩週內要看到量化效果)/ 生產採用率(一個月 50% 及格、三個月 80% 目標;Morgan Stanley 98% 天花板)/ 模式復用率(<30% 表示顆粒度或抽象質量有問題)/ 反哺平台貢獻(AER≥20% 健康,持續為零=諮詢陷阱)。四者關係:速度/效果/沉澱質量/飛輪。
- **最小文檔集**:Discovery Brief(無它不啟動)/ Pilot Charter(與業務發起人共簽)/ ADR / Go-live Checklist(無它不上線)/ Incident Runbook / Handoff Pack(無它不撤出)。不需要完美,必須存在。
- **治理紅線**:不把 FDE 當外包(對純定制需求有一票否決)/ KPI 不錯位(越快用最少定制跑通+提煉+撤離,激勵越高)/ 平台收割委員會(每週檢索一線代碼,高頻相似邏輯 30 天內抽象合流或下線)。
- **變更管理**:風險分級(低=直接做記錄/中=pod lead 確認/高=多資深評審+漸進+主動監控);所有生產變更要有驗證+回滾,非談判條件。
- **培訓 4 個月**:平台能力(讀 ADR+沙盒演練)→ shadowing 資深 FDE → 獨立負責子工作流 → 模板化沉澱貢獻。

### 中國語境

- **「包工包料」預期**:甲方只提需求+驗收。處理:合同寫明角色定義(聯合創新非代工交付,不同意就不做)/ 用「聯合實驗室、創新中心」形式降低阻力 / 讓甲方的人第一天就動手——用過就回不去。
- **遺留系統與數據孤島**:不替換舊系統,加適配層(API 對接,新能力覆蓋核心功能後自然淘汰)/ 數據先治標(腳本搬、接口對、中間表)再治本(平台團隊長期治理)/ 安全合規在 discovery 就設計,臨上線才過審會被一票否決。
- **兩種失敗同一根源**:IT 諮詢失敗=現場外包(什麼都做);SaaS 失敗=拒絕合理需求(什麼都不做)。根源相同:把產品當核心,沒把業務需求當核心。

### 人才畫像與培育

- **五維硬指標**:業務邏輯理解+系統設計 / 組織洞察與協調 / 結果驅動執行力(「叛逆者」,Shyam Sankar)/ 平台反哺意識 / 行業前沿意識(不跟上 AI 工具發展就掉隊)。
- **三階段面試**(遞進):① 戰壕測試——虛擬混亂客戶場景(40 年無文檔 DB2、敵意高管),測業務+客戶管理;否決:依賴完美 PRD、一味順從客戶。② 開放式情境評估——講解冷門業務規則後要求現場設計數據流+偽代碼,測可落地諮詢;否決:只給架構圖寫不出偽代碼。③ 教導型技術分享——講最自豪的複雜交付,測外循環抽象能力;否決:流水線固定任務、無獨立破局經歷。
- **業務側培訓五步**(約 3 個月,可獨立走):建立信心(先做單頁/插件/小工具)→ 雲端 HTML 單頁 → 雲端 Agent 工具 → Prompt/AI Skill → 抽象 Agentic Workflow。多數場景走到第二步就能搭可用 Demo。
- **技術側學業務**:沒有課程,只能嵌在真實項目裡(坐旁邊看→抽象流程圖→學追問「慢在哪」→一起做原型迭代)。兩路不對稱但終點同一:5.1 的五維人,回隊成為 FDE 種子。
- **五個坑**:只看技術不看業務翻譯 / 只看溝通不看動手(會做 PPT 寫不出代碼)/ 當更貴的顧問招(80% 時間開會寫文檔)/ 英雄工程師依賴(知識不沉澱,離職即停擺)/ 用成接需求工具人。

### 參考案例速記

- **Palantir**(起源,2005):CIA/NSA 需求無法文檔化→逼出 FDE。Delta 對單客戶 / Dev 對全客戶。Ship on Day One;Ontology 先建模;最長駐紮一年。2024 收入 $2.87B,公開回報 640%。
- **OpenAI**:呼叫中心語音評估框架→即時上報→重塑 Realtime API 底層+促成 Agent SDK。2026 Deployment Company 40 億美元+150 FDE。
- **Morgan Stanley × OpenAI**:eval framework 先行→試點→公司級擴展。98% 使用率、文檔可訪問率 20%→80%、資訊跟進數天→數小時。啟示:現場發現、評測治理、漸進擴展、組織採用四件事同時成立。
