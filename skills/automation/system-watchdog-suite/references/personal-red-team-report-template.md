```markdown
# 紅隊審計報告 — YYYY-MM-DD

掃描範圍：N 個 cron jobs（profile A + profile B）、N 個 skills、N 個專案目錄、跨 agent 記憶、內容管線、常駐服務。
方法：證據優先 — 讀 cron output 檔、executions.db、launchctl、git log、du、log 檔案；不臆測。

## 一、已修復（安全、可逆、已完成）

| # | 項目 | 動作 | 效果 |
|---|---|---|---|
| 1 | ... | ... | ... |

## 二、隱藏失敗（需要決策 — 見 brief-*）

### 🔴 P1-1 標題 → brief-NN
- 證據（路徑/時間戳/大小/log 行）

### 🟠 P2-1 標題 → brief-NN
- 證據

## 三、機會（系統性漏掉的）

1. 有數據支撐的機會（例：某渠道 N views 卻無自動化）

## 四、弱假設（明確點名）

| 假設 | 實際 |
|---|---|
| 記憶說「在跑」 | 實體查無 plist / 路徑已遷移 / 無 process |

## 五、決策執行紀錄（YYYY-MM-DD）

| Brief | 決策 | 執行狀態 |
|---|---|---|
| NN 主題 | A/B/C | ✅ 執行了什麼（含可逆性） |
| NN 主題 | 不做 | ✅ 維持現狀 |

待觀察：下次執行時間點（重啟首跑/改路由首跑等）。
```

## 分級標準

| 級別 | 定義 | 例子 |
|---|---|---|
| 🔴 P1 | 可能造成金錢/資料/時間損失，且使用者不知道 | 服務失聯、表單丟資料、自動化每天燒 token 後失敗 |
| 🟠 P2 | 明確浪費或結構性問題 | 幽靈 job、冷庫、重複簡報、磁碟垃圾 |
| 🟡 P3 | 機會或低風險確認 | 可系統化的高槓桿渠道、確認棄用 |

## 寫作規則

1. **每個發現帶證據**：路徑/時間戳/大小/log 行，缺證據就標「推測」
2. 已修復 vs 待決策分開，避免混在一起
3. 弱假設表 = 記憶/慣例 vs 實體不符的對照，是報告最有價值的部分
4. 決策執行紀錄在使用者回覆後更新，並同步記憶與跨 agent 共享檔
